Antes de empezar

Disco: /home está al 97 % (7,4 GB libres). src/_sweep ya ocupa 2,8 GB y el barrido de septiembre pidió ~15 GB entre clones y volúmenes. Antes del paso 4 liberá espacio (docker builder prune libera hasta 19 GB de caché de build sin tocar volúmenes) o el barrido se cae a mitad por «No space left on device».

  • RAM es el cuello de botella, no el disco. Cada corrida pica 1–2 GB. Con ~8 GB libres entran 6 corridas concurrentes; con menos, bajá --jobs.
  • Docker tiene que estar en un disco con espacio. Acá vive en /home/binaural80/docker-data-root; /var está casi lleno pero Docker no lo usa.
  • Las tres líneas comparten un solo Postgres (db-pg16), y eso condiciona varias decisiones más abajo.
  • Se necesita acceso SSH a los repos de binaural-dev para el fetch del paso 1.

refresh_pin() {
  local dest="$1" branch="$2"
  git -C "$dest" fetch --quiet origin "$branch" --tags
  git -C "$dest" checkout --quiet -B "$branch" FETCH_HEAD
  echo "$dest → $(git -C "$dest" rev-parse --short HEAD)"
}

refresh_pin src/_sweep/17.0/integra-addons             17.0
refresh_pin src/_sweep/l10nve_17.0/integra-addons      l10nve_17.0
refresh_pin src/_sweep/l10nve_17.0/odoo-venezuela      17.0
refresh_pin src/_sweep/19.0/integra-addons             19.0
refresh_pin src/_sweep/19.0/odoo-venezuela             19.0

# third-party-addons: solo dependencias, pero conviene que sigan la rama
for L in 17.0 l10nve_17.0; do refresh_pin src/_sweep/$L/third-party-addons 17.0; done
refresh_pin src/_sweep/19.0/third-party-addons 19.0

Anotá los hashes que imprime: son la trazabilidad del informe. Si algún checkout no existe (disco limpiado), usá clone_pin del runbook de septiembre.

2

Levantar las tres instanciasya definidas

Las tres ya están en instances.json (cov_17 :8101, cov_l10nve_17 :8102, cov_19 :8103); no hay que definirlas de nuevo. Hoy solo odoo-cov_19 está arriba. El bloque de configuración se conserva como referencia de por qué cada campo está donde está. 

// referencia — ya está en instances.json. Las otras dos: cov_17 (8101) y cov_l10nve_17 (8102).
"cov_19": {
  "odoo_version": "19.0",
  "external_port": 8103,
  "database": "pg16",
  "odoo_config": "default",
  "overwrite_odoo_config": {
    "addons": [
      "src/enterprise-19",
      "src/_sweep/19.0/integra-addons",
      "src/_sweep/19.0/odoo-venezuela",
      "src/_sweep/19.0/third-party-addons"
    ],
    "max_cron_threads": 0,
    "workers": 0,
    "mem_limit": "8g",
    "list_db": false,
    "db_filter": "^covs_19_"
  }
}

Cada campo está por una razón:

  • max_cron_threads: 0 — obligatorio. Sin esto la validación de aislamiento hace fallar el build, porque varias instancias comparten Postgres y el cron no respeta el db_filter.
  • mem_limit: "8g" — el default son 4 g, y un OOM dentro del contenedor puede matar el PID 1. Con 8 g entran 3 corridas.
  • list_db: false + db_filter — mantienen las bases del barrido fuera del selector de todo el mundo.

La clave es db_filter, no dbfilter. El generador lee db_filter (compose_generator.py:240); un dbfilter se ignora en silencio. Hay una instancia en producción con ese error hoy.

# build regenera compose y nginx pero NO recrea los contenedores que están corriendo.

# (solo si cambió instances.json o la config; si no, basta con el up)
./odoo build --no-confirm

# levantar solo los tres nuevos

3

Rehornear las plantillascada mes

Sin plantilla, cada módulo arranca instalando base, web, account… desde cero. Con plantilla, ese arranque son segundos. Medido sobre un módulo chico: 73 s sin plantilla contra 25 s con plantilla, y la diferencia crece con el peso del árbol de dependencias.

Las de septiembre traen el estado de entonces: --force revierte las banderas, las borra y las hornea de nuevo sobre el Odoo actual. Una por versión de Odoo — el esquema no es compatible entre versiones. Las dos líneas de 17 comparten tpl_cov_17, porque la plantilla solo trae módulos del core. 

./scripts/coverage-sweep template --instance cov_17 --db tpl_cov_17 --force
./scripts/coverage-sweep template --instance cov_19 --db tpl_cov_19 --force

✅ Plantilla 'tpl_cov_19' lista en 91s: 111 módulos instalados, 65 MB, blindada.

«Blindada» significa IS_TEMPLATE true + ALLOW_CONNECTIONS false. Con datallowconn=false sigue sirviendo como origen de CREATE DATABASE —es el estado de template0— pero deja de poder abrirse, así que nadie la modifica por accidente y el error «is being accessed by other users» se vuelve inalcanzable. Para rehornearla, --force revierte las dos banderas antes de borrarla.

Los 9 módulos de la plantilla (base, web, mail, contacts, account, product, stock, sale, purchase) son parte del método: cambiarlos cambia el estado de la base que ven los tests at_install, y rompe la comparabilidad con las mediciones anteriores.

4

Los tres barridos

Fijá la fecha de corte una vez y usala en todos los comandos de la sesión:

export FECHA=$(date +%F)   # ej. 2026-10-05

Se pueden correr en paralelo, en terminales distintas o con &. Reparte --jobs según la RAM libre: la suma de los tres es la concurrencia real. 

./scripts/coverage-sweep run --instance cov_17 --line 17.0 --slug 17 \
    --repos integra-addons \
    --out logs/coverage-sweep/${FECHA}_17.0 \
    --db-template tpl_cov_17 --jobs 2 --timeout 2400

./scripts/coverage-sweep run --instance cov_l10nve_17 --line l10nve_17.0 --slug l10nve17 \
    --repos integra-addons,odoo-venezuela \
    --out logs/coverage-sweep/${FECHA}_l10nve_17.0 \
    --db-template tpl_cov_17 --jobs 2 --timeout 2400

./scripts/coverage-sweep run --instance cov_19 --line 19.0 --slug 19 \
    --repos integra-addons,odoo-venezuela \
    --out logs/coverage-sweep/${FECHA}_19.0 \
    --db-template tpl_cov_19 --jobs 3 --timeout 2400

→ Escaneando manifests en odoo-cov_19... 216 módulos en los repos medidos · 202 medibles · 14 descartados por dependencias 0 ya medidos (se saltean) · 202 por medir [1/202] · binaural_account_asset 53% sin_tests 25s | ETA 1h02m

  • --slug tiene que casar con el db_filter de la instancia (19 ↔ ^covs_19_), o las bases del barrido le aparecen a todos en el selector.
  • --timeout 2400 es detector de colgadas, no presupuesto. Ningún módulo lo alcanzó; el más lento tardó 850 s.
  • Es reanudable. Si se corta, el mismo comando retoma donde quedó. La clave de caché es un fingerprint de módulo + commit del repo + plantilla + timeout, así que si el código cambió el módulo se vuelve a medir en vez de devolver un número viejo. Este barrido se corrió en tres tramos y sumó 564/564.

Auditar y rehacer lo que salga marcado

Este paso no es opcional. La auditoría detecta mediciones que describen archivos de otro módulo — datos falsos que se ven perfectamente válidos. En este barrido marcó 17 de 564. 

for L in 17.0 l10nve_17.0 19.0; do
  ./scripts/coverage-sweep status --out logs/coverage-sweep/${FECHA}_$L
done

Dataset e informe

# la línea base de octubre ES el dataset de septiembre, convertido de formato
./scripts/coverage-sweep-to-baseline \
    --dataset deliverables/coverage-sweep/dataset-2026-09.json \
    --out deliverables/coverage-sweep/baseline-2026-09.json

./scripts/coverage-sweep-aggregate \
    --run 17.0=logs/coverage-sweep/${FECHA}_17.0 \
    --run l10nve_17.0=logs/coverage-sweep/${FECHA}_l10nve_17.0 \
    --run 19.0=logs/coverage-sweep/${FECHA}_19.0 \
    --baseline deliverables/coverage-sweep/baseline-2026-09.json \
    --baseline-map 17.0=17.0 --baseline-map l10nve_17.0=l10nve_17.0 --baseline-map 19.0=19.0 \
    --measured-at " de octubre de 2026" \
    --out deliverables/coverage-sweep/dataset-2026-10.json

./scripts/coverage-sweep-report \
    --dataset deliverables/coverage-sweep/dataset-2026-10.json \
    --out deliverables/coverage-sweep/informe-2026-10.html \
    --title "Cobertura de las tres líneas"

--baseline-map dice a qué versión de la línea base corresponde cada línea de hoy, y --diverged marca los (línea, repo) cuya rama se bifurcó de la que se midió antes: su delta existe pero no es like-for-like, y el informe lo declara en vez de dejar que se lea como progreso.

antes de publicar cualquier comparación

./scripts/coverage-sweep-aggregate --selftest \
    --baseline deliverables/coverage-sweep/baseline-2026-09.json

--baseline-map dice a qué versión de la línea base corresponde cada línea de hoy. Con la base de septiembre las versiones son las propias etiquetas de línea (17.0=17.0, etc.), porque septiembre ya distingue 17.0 de l10nve_17.0; la de agosto solo tenía 17 y 19. Ya no hace falta --diverged l10nve_17.0:integra-addons: esa bifurcación era respecto de agosto. Si una rama base se reescribió desde septiembre, agregá --diverged LINEA:REPO para ese par.

Si no hay línea base, --baseline se omite y el dataset sale solo con el estado actual, sin sección de progreso. El resto funciona igual.

Las cuatro trampas, más una de octubre

Las cuatro produjeron datos incorrectos que se veían válidos. Todas están corregidas en la herramienta; van acá porque explican por qué el código tiene las defensas que tiene, y conviene no «simplificarlas» después.

El archivo de datos de coverage 17 mediciones falsas

coverage guarda sus datos en .coverage en el directorio de trabajo, que dentro del contenedor es el mismo para todas las corridas. Dos módulos midiéndose en paralelo compartían el archivo: uno hacía erase mientras el otro escribía, y el reporte de uno terminaba describiendo los archivos del otro.

Se descubrió porque dos módulos distintos daban cifras idénticas: 939 sin cubrir de 1.188.

Corregido: COVERAGE_FILE por corrida. Y la auditoría del paso 5 existe justamente para detectar el residuo.

Nombres de base truncados colisión garantizada

Postgres corta en 63 caracteres, así que el nombre del módulo hay que recortarlo. Pero recortarlo a secas colisiona: hay 5–6 pares por línea que comparten los primeros 30 caracteres (binaural_subsidiary_payment_advance y …_advance_igtf) y además quedan adyacentes en orden alfabético, o sea que la cola los despacha juntos. Los dos apuntaban a la misma base.

Corregido: al recorte se le suma un hash del nombre completo, así la unicidad no depende de cuánto se recortó.

Emparejar versiones al comparar deltas de 70 puntos

La línea base tiene una fila por módulo y por versión. Indexarla solo por (repo, módulo) hace que una versión sobrescriba la otra, y entonces se compara la 17 de hoy contra la 19 de agosto. Eso produce «caídas» de 98 % a 26 % que no son caídas: son dos versiones distintas del mismo módulo.

Corregido: la clave es (versión, repo, módulo) y --baseline-map es obligatorio y explícito, para que nadie lo haga por accidente.

--only y la lista de trabajo excluidos perdidos

Una corrida con --only calculaba una lista de trabajo de solo esos módulos y sobrescribía la del barrido completo — que es de donde el informe saca los módulos que no se pudieron medir por dependencias. En la línea 19.0 son 14.

Corregido: con --only la lista de trabajo se conserva.

Formato de la línea base sale sin progreso

dataset-2026-09.json no se puede pasar a --baseline tal cual: guarda lines y dos criterios por módulo (pct sin archivos de test, pct_all con ellos), mientras la base espera versions con un solo criterio. coverage-sweep-to-baseline promueve el criterio *_all —el que usó agosto y contra el que compara build_progress— y deja el --selftest en verde (verificado el 30 de septiembre en las tres líneas).

Limitación conocida

El escaneo de módulos los identifica por el nombre de su carpeta. Cuando un mismo nombre existe en los dos repositorios de una línea —hoy pasa solo con l10n_binaural— se mide uno de los dos y el otro queda fuera. Son 2 módulos sobre 564. Arreglarlo requiere cambiar el escaneo, que lo comparte scripts/odoo-test.

Al terminar

Los tres contenedores cov_* y sus checkouts se pueden dejar: reusarlos hace que el próximo informe arranque en el paso 4. Si hace falta el espacio: 

# los logs de septiembre (97 MB) se pueden archivar; el dataset ya los resume

# bases de barrido que hayan quedado colgadas (acotado a una línea con --slug)
./scripts/coverage-sweep clean --instance cov_19 --slug 19 --yes

# bajar los contenedores del barrido, sin tocar los demás
docker compose -f docker-compose.generated.yml stop odoo-cov_17 odoo-cov_l10nve_17 odoo-cov_19

# y si además querés el disco
rm -rf src/_sweep
